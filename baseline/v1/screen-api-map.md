# IntentLock v1 화면–API 대응표

## 화면과 API 연결

| 기능 | 화면 입력·표시 | API | 요청 필드 |
|---|---|---|---|
| 로그인 | 아이디, 비밀번호 | POST /auth/login | username, password |
| 로그인 계정 확인 | 아이디, 로그인 계정 권한 | GET /auth/me | 없음 |
| 직원 목록 | 이름, 이메일, 부서, 현재 권한 | GET /employees | 없음 |
| 권한 변경 | 대상 직원, 기존 권한, 변경할 권한 | PATCH /employees/{employee_id}/role | 경로: employee_id, 본문: role |
| 개인정보 내보내기 | 대상 직원 목록, 인원수, 선택 항목 | POST /exports | employee_ids, fields |
| 실행 기록 | 작업 종류, 실행 계정, 대상, 변경 내역, 시각 | GET /audit-logs | 없음 |

## 권한 변경 정상 흐름

1. 관리자 계정으로 로그인한다.
2. 직원 목록에서 변경할 직원을 선택한다.
3. 확인 창에서 대상 직원과 기존·변경할 권한을 확인한다.
4. 취소하면 요청을 보내지 않는다.
5. 실행하면 서버가 관리자 권한을 검사한다.
6. 직원 권한 변경과 실행 기록을 함께 저장한다.
7. 화면의 직원 목록과 실행 기록을 갱신한다.

요청 예시:

PATCH /employees/1/role
Content-Type: application/json

{"role": "admin"}

직원의 기존 권한은 확인 화면에 표시되지만 요청 본문에는 포함되지 않는다.
서버는 변경 시점의 DB에서 기존 권한을 읽는다.

## 개인정보 내보내기 정상 흐름

1. 관리자 계정으로 로그인한다.
2. 내보낼 직원과 개인정보 항목을 선택한다.
3. 확인 창에서 대상 직원, 인원수, 항목을 확인한다.
4. 실행하면 서버가 관리자 권한과 요청값을 검사한다.
5. 선택한 직원·항목만 포함한 CSV를 생성한다.
6. 실행 기록을 저장하고 CSV를 응답한다.

요청 예시:

POST /exports
Content-Type: application/json

{"employee_ids": [1, 2], "fields": ["name", "email"]}

인원수는 employee_ids의 개수로 산출하며 별도 요청 필드로 보내지 않는다.

## 현재 구현 범위

- 관리자 1개·일반 사용자 2개의 테스트 계정
- 가상 직원 10명
- 비밀번호 해시와 JWT 로그인
- 관리자 접근 제어
- 직원 권한 변경과 실행 기록
- 선택한 개인정보의 CSV 내보내기
- 실행 전 확인 화면
- API 및 화면 자동화 테스트

employees.role은 관리 대상 직원의 권한이다.
users.role은 실습 서비스에 로그인하는 계정의 권한이다.
현재 직원 권한 변경은 로그인 계정 권한을 변경하지 않는다.

## 현재 한계와 후속 구현

현재 확인 창은 사용자에게 실행 내용을 보여주는 화면이다.
확인 창을 거쳤다는 사실을 서버가 검증하는 기능은 아직 없다.

후속 단계에서 다음 기능을 구현한다.

- 승인 데이터와 실제 실행 요청의 일치 여부 검증
- 승인 만료·재사용·승인 후 상태 변경 검사
- AI의 화면·API 변경 분석
- AI의 표시 누락·위험 후보·변조 테스트 제안
- 개발자의 AI 제안 검토와 확정

## AI 평가용 변경 사례

내보내기 API에 새로운 개인정보 항목을 추가하고,
확인 화면에는 해당 항목을 표시하지 않는 변경 버전을 만든다.

AI가 v1과 변경 버전의 화면·API를 비교하여
불일치를 발견하고 관련 테스트를 제안하는지 평가한다.
